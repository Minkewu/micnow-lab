# MicNow Lab 客户端实测记录

测试日期：2026-11-13。Skill 版本：0.5.0；测试源：[GitHub 提交 925b0ed](https://github.com/Minkewu/micnow-lab/commit/925b0ed25576cc44a0b2af0afc0a8ce61258ac1c)。环境：macOS ARM64。新增 CLI 和测试 Skill 使用独立目录；Codex 与 WorkBuddy 使用已有客户端。

本轮完成了 Codex CLI 的模型调用、模拟设备操作和独立 HTTP 核验。其他客户端的结果停留在不同阶段，不能合并为“全部平台运行通过”。本页只保留脱敏结果，不公开账户标识、本机绝对路径、会话凭据或原始会话日志。

## 如何理解结果

1. **客户端安装与基本命令**：真实客户端能返回版本和帮助。这不代表账户已登录，也不代表所有可选运行组件均已验证。
2. **Skill 安装与发现**：文件复制和完整性校验只是安装步骤；只有客户端自己的技能目录或新模型会话实际列出、读取该 Skill，才记为“发现通过”。插件清单解析成功也不等于模型已调用。
3. **模型运行实验室**：实际模型会话发现 Skill，启动随包服务，执行设置、回读与跨端比较，最后关闭服务。仅预检命令、客户端本身的服务启动或自动化单元测试，均不计入这一层。

## Codex CLI：实际运行通过的范围

使用官方 Skill 安装工具，从上述固定 GitHub 提交安装到项目 `.agents/skills/micnow-lab/`。真实的新 CLI 会话读取 Skill 后，用 Python `3.9.6` 启动了本机服务与独立模拟设备子进程。

| 操作 | 实际结果 |
| --- | --- |
| 读取初始状态 | revision 0，`RightOption` / `hold` |
| AI 仅把 Speak 改为 `toggle` | revision 1；原快捷键保留，写入后核验通过 |
| 独立 HTTP 请求使用 `source=web`，仅将快捷键改为 `LeftOption` | revision 2；CLI 回读相同设置 |
| AI 仅把 Speak 改回 `hold` | revision 3；保留 Web 设置的 `LeftOption` |
| 模拟 Speak 按下、释放、演练 | 返回预置文本，`audio_captured=false`；结束时 `active=false`、`pressed=false` |
| 调用随包 `shutdown` | 服务和模拟器退出，端口关闭，连接文件及本次运行目录清除 |

四次 CLI/HTTP 比较中的设备会话、设置和 revision 均相同。19 个 Skill 文件在运行前后保持一致，并与发布源逐项校验相同。

初始受限环境拒绝本机监听和通信；使用客户端正常权限申请流程后完成。未使用跳过权限检查的运行模式，也未修改安全配置。这里验证的是实际模型到本机 CLI/HTTP 的链路：HTTP 请求覆盖网页使用的接口，但本轮没有点击可视网页，因此不把它写成浏览器界面验收。也不将这一结果自动推广到 Codex 桌面、Windows、Linux、远程容器或真实硬件。

## Gemini：临时信任实验与正常使用步骤

本轮默认 `gemini skills list --all` 跳过了未受信任项目中的技能。尝试 `--skip-trust skills list --all` 返回参数错误；随后只有设置临时进程环境 `GEMINI_CLI_TRUST_WORKSPACE=true` 的列表命令显示 `micnow-lab [Enabled]`。模型预检同样使用了临时跳过信任的选项，最终因缺少认证方式退出，错误码为 41。

这证明特定临时信任条件下客户端能解析该 Skill；**不证明正常默认安装、交互信任授权、模型激活或 Python 工具执行已通过**。这两种临时选项不应出现在面向普通用户的默认安装命令中。

正常使用项目 Skill 时：

1. 在希望使用 Skill 的项目中完成目录安装，然后从同一项目交互启动 `gemini`。
2. 审阅客户端显示的项目配置和技能；出现信任提示时，确认后选择 **Trust folder**，仅信任这个项目。需要调整已有决定时，在本次测试版本中使用 `/permissions trust` 打开当前项目的正常信任对话框。
3. 通过客户端的正常流程选择或完成账户认证。技能安装不会替代这一环节。
4. 在会话中执行 `/skills reload`、`/skills list`，确认 `micnow-lab` 出现，再请求模型打开实验室，按提示批准技能激活及必要命令。

信任对话框和管理方式见 [Gemini 官方受信任文件夹说明](https://geminicli.com/docs/cli/trusted-folders/)；技能列表、重载与激活见 [官方技能入门](https://geminicli.com/docs/cli/tutorials/skills-getting-started/)。`/permissions trust` 已与本次安装的 0.68.0 客户端内置命令核对；部分教程仍写 `/trust`，其他版本应以其实际帮助为准。认证使用 [官方认证流程](https://geminicli.com/docs/get-started/authentication/)。以上正常交互流程仍需补做实际验收。

## Qwen 与 Kimi：本地安装和目录发现通过

Qwen 的真实本地路径扩展安装成功，初始化后的客户端将 `micnow-lab` 列为项目技能，将 `micnow-lab:micnow-lab` 列为扩展技能，状态均为 `ok`。`modelInvocable=true` 表示注册为可调用技能，并不表示模型已经调用。本轮没有验证 GitHub URL 或 ZIP URL 的原生扩展安装，也没有运行实验室。

Kimi 的真实本地路径插件安装成功，插件启用且无清单错误。客户端技能目录列出了项目技能和限定名 `micnow-lab:micnow-lab`。单独传入 `--skills-dir` 的一次探测没有使 Web 工作区目录显示该技能；放在项目 `.agents/skills/micnow-lab/` 后实际发现通过。本轮没有验证 GitHub URL 或 ZIP URL 插件安装，也没有运行实验室。测试用客户端服务已关闭。

两者均需在可用模型和正常权限条件下继续验证“模型调用 Skill → 启动实验室 → 双向设置与回读 → 退出清理”，才能升级运行结论。

## 后续验收

登录或选择模型后，应使用同一个测试项目，先确认客户端实际发现 Skill，再让模型完成启动、读取、修改、回读、模拟 Speak 和关闭清理。浏览器验收应另外确认真实页面能打开、页面修改能被 Agent 回读，并明确记录可视操作与 HTTP 接口测试的区别。

目前已记录的阻塞发生在客户端认证、模型配置、项目发现、下载或文件选择阶段；这不足以证明这些平台的 MicNow Lab 运行成功，也不足以判定平台不支持。所有已通过结果均针对模拟设备，不涉及真实录音、USB 设备、固件或外部应用控制。
